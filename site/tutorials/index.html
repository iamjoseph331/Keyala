Run the local mock

The demo starts a disposable Rust server with fake OpenAI and Anthropic keys and a mock provider. It never sends a live provider request. Use the phone for the real consent path, or use the scripted simulation when Xcode is unavailable.

Open the iOS project in Xcode and run it in a simulator. In Settings, turn off Demo mode, set the server URL to http://localhost:8080, and enable Allow HTTP for localhost. In Account, sign in as demo@masterkey.dev. The script prints the chat example command. Start it in another terminal, open http://localhost:3000, connect, then review and approve the request on the phone.

Terminal 1Scripted phone simulation

The simulation approves pending connections and requests from a script. It demonstrates the backend flow; it is not an iOS app test. Press Ctrl+C to stop either demo and remove its temporary database.

Requirements: Rust/Cargo, curl, jq, and openssl. The chat example also needs Node.js 20+. The scripted phone mode also needs sqlite3. Choose another port with PORT=8091 if 8080 is occupied.

Backend integration

Register and connect a server app

Create an app in the developer console or use the terminal recipe below. Keep app_secret in server-side secret storage. It authenticates connection creation and polling; it is not a model grant and must never be shipped to a browser.

Register onceSave the returned app_secret
export MK_URL=http://localhost:8080

curl -sS -X POST "$MK_URL/v1/apps" \
  -H 'Content-Type: application/json' \
  -d '{"name":"My app","homepage":"https://example.com"}'

Save both returned values: app_id identifies the app, and app_secret starts server-side connections. Ask the user which provider to connect, then create a short-lived connect code:

Create a connectionRun on your backend
curl -sS -X POST "$MK_URL/v1/connect" \
  -H "Authorization: Bearer $MK_APP_SECRET" \
  -H 'Content-Type: application/json' \
  -d '{"vendor":"openai"}'

Show the returned connect_url or code to the user. The phone displays the app and provider. A user's first grant for your app must use ask, so each model request needs its own approval. They can widen access later in Grants.

Poll the returned code from the server until the user approves. The approved response includes grant_token exactly once. Store that token on your backend, scoped to the authenticated app user and provider. Export it as MK_GRANT_TOKEN only for local testing.

Poll the connectionDo not log tokens
curl -sS "$MK_URL/v1/connect/$CONNECT_CODE" \
  -H "Authorization: Bearer $MK_APP_SECRET"

For an SDK integration, use the official client with the MasterKey route and automatic retries disabled. Keep the vendor-specific grant scoped to the user session and provider.

Supported calls

Send text, then handle approval

Use the familiar request body, a vendor-specific grant, and a stable idempotency key for each logical operation. Disable automatic SDK retries. The server checks the policy before forwarding the request.

First OpenAI request with curlReturns a request ID while approval is pending
request_key=$(openssl rand -hex 16)
curl -sS -i "$MK_URL/v1/openai/chat/completions" \
  -H "Authorization: Bearer $MK_GRANT_TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'X-MasterKey-Wait: 0' \
  -H "Idempotency-Key: $request_key" \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"Say hello."}],"max_tokens":32}'

In a server integration, inspect the HTTP status before decoding the body as a provider response. The SDK examples below show the immediate-success path.

OpenAI compatible routePOST /v1/openai/chat/completions
from openai import OpenAI

client = OpenAI(
    base_url=f"{MK_URL}/v1/openai",
    api_key=grant_token,
    max_retries=0,
)

reply = client.chat.completions.create(
    model="gpt-4.1-mini",
    messages=[{"role": "user", "content": "Summarize this text."}],
    max_tokens=300,
    extra_headers={"Idempotency-Key": operation_id},
)
Anthropic compatible routePOST /v1/anthropic/messages
from anthropic import Anthropic

client = Anthropic(
    base_url=f"{MK_URL}/v1/anthropic",
    api_key=grant_token,
    max_retries=0,
)

reply = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=300,
    messages=[{"role": "user", "content": "Summarize this text."}],
    extra_headers={"Idempotency-Key": operation_id},
)

Only allowlisted models work. The current names are gpt-4o, gpt-4o-mini, gpt-4.1, gpt-4.1-mini, claude-opus-5-5, claude-sonnet-5-5, and claude-haiku-5-5. Output has a server-enforced cap; when omitted, MasterKey injects the model's default. Streaming and non-text content are rejected. Check the server pricing allowlist before selecting models in your app.

When the response is not ready

  1. 202 Accepted: approval is still pending. Read request_id and poll GET /v1/requests/{id} with the same grant until the status is terminal.
  2. 504 masterkey_uncertain: the upstream call may have been sent, but its outcome is unknown. Poll the existing request ID. Never issue a new model POST to recover.
  3. Completed: use the stored response. Actual cost can be null when the provider did not return usage.
Poll an existing requestUse the body ID or X-MasterKey-Request-Id header
curl -sS "$MK_URL/v1/requests/$REQUEST_ID" \
  -H "Authorization: Bearer $MK_GRANT_TOKEN"

Retry rule: retrying the same logical POST with the same Idempotency-Key and body returns the existing outcome. A different body under that key returns 409 idempotency_conflict. Keep the key stable across transport retries and poll the request after a timeout.

Static browser app

Connect without an app secret

A static site can request browser access using its registered origin. Register allowed_origins for your exact HTTPS origin, or ask the server operator to declare the app. Registration returns an app_id and an app_secret. Use only the app ID in client code and store the secret securely for the developer console.

Register a public appServer or operator setup
curl -sS -X POST "$MK_URL/v1/apps" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Static tool","allowed_origins":["https://example.com"]}'

From the page, send {"app_id":"...","vendor":"openai"} to POST /v1/connect. The response contains connect_code and a one-time-connection connect_secret. Use that secret only to poll GET /v1/connect/{code}; on approval, claim the one-time grant and use it as a bearer token for proxy calls. The browser API routes allow CORS for this flow. Do not put an app secret in client code.

The browser's Origin is a browser-enforced signal, not an identity proof. The phone shows the origin so the user can compare it to the page. The grant is available to JavaScript on that page, so guard against script injection and keep the initial ask-only policy.

See the working Resume Tailor sample app. It is a static page with no vendor key or app server; visitors connect their own key and approve each call on their phone.

Review usage and cost

Open the developer console, enter the app token for the same server, and pick a range. Daily request volume, known model costs, and model and country tables are scoped to that app.

Known cost uses vendor-reported usage. The estimate is the pre-call reservation, and some completed requests have missing usage. Country is an approximation based on the phone network when the connection was approved. Unavailable locations appear as Unknown.

The hosted free service loses report history, grants, and provider keys on restart. A new app token can restore its app registration if the server keeps the same master key. Run with persistent storage to retain reports and ensure old tokens stay revoked after rotation.

Fetch an aggregate reportUse the app token
curl -sS "$MK_URL/v1/app/report?days=30" \
  -H "Authorization: Bearer $MK_APP_SECRET"

Recovery and limits

Make failures visible

400 model_not_allowed
Choose a model from the server's vendor allowlist.
400 unsupported_content / unsupported_option
Send plain text and supported options only. Images, audio, files, tools, and streaming are outside v1.
400 policy_not_allowed_yet
Retry the pending first connection with the ask policy. The user may widen it later in Grants.
403 masterkey_denied
Tell the user the request was denied. Do not submit it again automatically.
401
The credential is invalid, revoked, or was lost in a server reset. Reconnect if your grant has been rejected.
410 masterkey_expired
The request expired before approval. Ask the user before starting a fresh request.
429 or 5xx
Respect rate limits and service errors. Use an idempotency key, avoid automatic retries for model POSTs, and inspect the original request when its outcome is unclear.

Cost shown before approval is a reservation estimate, not a provider guarantee. MasterKey reserves against the request and settles from provider-reported usage when available. Users can inspect request history and revoke grants; your app should still handle a revoked grant or unavailable server cleanly.
